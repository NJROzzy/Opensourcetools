Welcome to Amalgam

A field guide for students, developers, and curious builders who want to make real projects with free, open-source tools. We’ll design a small system together, then help you start a project of your own.

Why Amalgam exists

I built Amalgam to help you go from “I have an idea” to “I know what I need to build it.” It shows what each tool does, where it fits, and how the pieces work together.

How Amalgam works

Imagine a greenhouse grower who wants to check the temperature from anywhere. We’ll work from that request to a design you can draw in the System Design Canvas.

Start with what the grower needs, then sketch how a reading travels, decide what happens when something breaks, and choose tools once each component has a job.

Start with the requirements

The grower needs to see the latest temperature and the last seven days of readings. For this first version, assume one greenhouse, one sensor, and one reading per minute.

Write down what success looks like: the dashboard shows a reading less than two minutes old while the sensor is online. Keep automatic climate control out of this first version.

Try it: How many readings will you store each day?

One reading per minute × 60 minutes × 24 hours gives 1,440 readings per day. Estimate traffic and storage before deciding whether you need more infrastructure.

Sketch how data moves

Draw one box for each job. Label each arrow with what moves across it or what the next component asks for.

  1. SensorSends a reading
  2. CollectorValidates and saves it
  3. DatabaseStores the history
  4. DashboardQueries and displays it

To make the sketch concrete, follow one message through it. A reading contains a device ID, a timestamp, and the temperature in Celsius. The dashboard queries for recent readings and plots them over time.

Design for a failure

Suppose the greenhouse loses Wi-Fi. The sensor can buffer recent readings and send them when the connection returns. Meanwhile, the dashboard can show when it last received a reading and flag stale data.

Try it: What if a retry sends the same reading twice?

Give each reading a stable ID. Store it only once so retries don’t create duplicate points on the chart.

Choose tools and test the design

For this version, you could use a Zephyr device, a small HTTP collector, PostgreSQL for history, and Grafana for charts. A single collector is enough to start. Consider an MQTT broker if you later need devices to publish to multiple consumers.

Test the smallest complete path first. Send one sample reading, confirm it’s stored, and look for it on the chart. Then disconnect the sensor and check both the stale-data warning and recovery.

In the System Design Canvas, choose Blank canvas, add the four boxes, and label their connections. Keep the requirements and failure behaviour in notes beside the diagram.

What hardware can you design?

  • Circuit boards and enclosures with KiCad and FreeCAD.
  • Sensor nodes and embedded devices with Zephyr and PlatformIO.
  • Digital logic and processor designs with Verilator and Yosys.

      § 7

      Method

      On inclusion. A tool enters the Atlas only if it can be used at no cost and its source is published under a recognised open licence (MIT, Apache-2.0, BSD, GPL, MPL and kin). For open-weight AI models, only releases under an open-source licence (Apache-2.0) are recommended. Nothing here requires a paid plan. Where a project moved to a source-available licence, the Atlas lists its open community fork instead.

      On assembly. A proper project is rarely one tool, or one domain — it is an amalgam. A robotics study might braid ROS 2, MuJoCo and PyTorch; an IoT monitor braids KiCad, Zephyr, MQTT and Grafana across hardware, networks and data. Every tool is tagged with each domain it serves, which is how the map places it. Read the Atlas as a set of parts, not a ranking.

      On currency. Licences change. Always verify the licence file in a project's repository before you build upon it.
